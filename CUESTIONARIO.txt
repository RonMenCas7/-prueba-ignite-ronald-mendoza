PREGUNTA 2 — ESTRUCTURAS DE DATOS
===============================================================================

Selecciona la estructura de datos más apropiada para cada caso:

1. Procesar solicitudes en el orden en que llegaron.
2. Implementar la función "deshacer" de un editor.
3. Buscar rápidamente un usuario mediante un identificador único.
4. Representar las conexiones entre usuarios de una red social.

Para cada caso explica:

- la estructura elegida;
- cómo funciona;
- el costo aproximado de insertar, buscar o retirar elementos;
- una alternativa y por qué sería mejor o peor.

RESPUESTA:

1, para procesar solicitudes en el orden en que llegaron usaría una cola, FIFO, entra primero y sale primero, pero ojo con implementarla usando `array_shift` en un array de PHP porque cada retiro puede reindexar y terminar siendo O(n), mejor usar `SplQueue` o manejar dos indices, asi insertar y retirar queda en O(1), una pila no sirve porque cambia el orden, y una cola de prioridad solo tendría sentido si hay prioridades

2, para deshacer usaría una pila, LIFO, la ultima accion es la primera que se deshace, con `push` y `pop` normalmente es O(1), para rehacer tendría otra pila porque si no pierdo lo que acabo de deshacer, como alternativa una lista doblemente enlazada permite moverse en ambos sentidos pero ocupa mas memoria, no se si para un editor simple valga la pena

3, para buscar por id unico usaría una tabla hash, en promedio buscar, insertar o retirar es O(1), aunque en el peor caso por colisiones puede ser O(n), en PHP un array asociativo ya funciona bastante parecido para este uso, una alternativa sería un árbol balanceado, que tarda O(log n) pero mantiene el orden y permite consultas por rangos, en una base de datos normalmente esto se resolvería con un indice

PREGUNTA 3 — PROBLEMA SENCILLO DE PHP
===============================================================================

Implementa la siguiente función PHP:

function countWords(string $text): array
{
    // Implementación
}

La función debe:

- convertir el texto a minúsculas;
- ignorar signos de puntuación;
- separar las palabras aunque existan varios espacios;
- ignorar elementos vacíos;
- contar cuántas veces aparece cada palabra;
- ordenar el resultado de mayor a menor frecuencia;
- en caso de empate, ordenar alfabéticamente;
- devolver un arreglo asociativo.

Ejemplo:

$text = 'PHP es útil. Laravel usa PHP; PHP es un lenguaje.';

Resultado esperado:

[
    'php' => 3,
    'es' => 2,
    'laravel' => 1,
    'lenguaje' => 1,
    'un' => 1,
    'usa' => 1,
    'útil' => 1,
]

Explica:

- las funciones de PHP que utilizaste;
- cómo manejaste la puntuación y los espacios;
- qué sucede si el texto está vacío;
- cómo harías que funcione correctamente con Unicode y acentos.

RESPUESTA:

Mi primera idea seria `explode(' ', strtolower($text))`, pero ahi aparece el problema, los signos quedan pegados a las palabras y con varios espacios aparecen elementos vacios, asi que no me sirve mucho

Mejor separo por todo lo que no sea letra o numero con `preg_split` y la expresion `/[^\p{L}\p{N}]+/u`, el `+` agrupa varios separadores seguidos y `PREG_SPLIT_NO_EMPTY` evita devolver palabras vacias, el `/u` hace que trabaje con UTF-8

Despues uso `array_count_values` para contar y `uksort` para ordenar las claves, primero comparo la frecuencia y si empatan uso `strcmp` para orden alfabetico

```php
function countWords(string $text): array
{
    $text = mb_strtolower($text, 'UTF-8');

    $words = preg_split('/[^\\p{L}\\p{N}]+/u', $text, -1, PREG_SPLIT_NO_EMPTY);

    if ($words === false || $words === []) {
        return [];
    }

    $counts = array_count_values($words);

    uksort($counts, function (string $a, string $b) use ($counts): int {
        return $counts[$b] <=> $counts[$a] ?: strcmp($a, $b);
    });

    return $counts;
}
```

si el texto esta vacio o solo tiene puntuacion devuelve un array vacio, no hace falta tratarlo como un error

para unicode uso `mb_strtolower` en vez de `strtolower` y `\p{L}` para que tambien reconozca letras con acentos o ñ, si quisieran que `util` y `útil` se consideren la misma palabra tendria que normalizar usando `Normalizer` de intl, pero eso ya depende de lo que se espera

PREGUNTA 4 — COMPLETAR CONSULTA SQL
===============================================================================

Considera estas tablas PostgreSQL:

users
-----
id          BIGINT PRIMARY KEY
name        VARCHAR(255)
email       VARCHAR(255)

orders
------
id          BIGINT PRIMARY KEY
user_id     BIGINT REFERENCES users(id)
status      VARCHAR(30)
total       NUMERIC(12,2)
created_at  TIMESTAMP

Completa la consulta para obtener todos los usuarios, incluyendo aquellos que
no tienen compras aprobadas en los últimos 30 días.

El resultado debe contener:

- user_id;
- name;
- approved_order_count;
- total_spent.

Los usuarios sin compras deben mostrar 0. El resultado debe ordenarse desde el
mayor total gastado hasta el menor.

SELECT
    u.id AS user_id,
    u.name,
    ______________________________ AS approved_order_count,
    ______________________________ AS total_spent
FROM users u
______________________________ orders o
    ON ______________________________
    AND o.status = 'APPROVED'
    AND o.created_at >= CURRENT_TIMESTAMP - INTERVAL '30 days'
GROUP BY ______________________________
ORDER BY ______________________________;

Explica:

- por qué elegiste ese tipo de JOIN;
- por qué los filtros de estado y fecha deben colocarse en esa cláusula;
- para qué sirve COALESCE;
- qué sucedería si los filtros se colocaran directamente en WHERE.

RESPUESTA:

La frase "todos los usuarios, incluso los que no tienen compras" ya me hace pensar en `LEFT JOIN`, porque con un `INNER JOIN` esos usuarios directamente desaparecerian

```sql
SELECT
    u.id AS user_id,
    u.name,
    COUNT(o.id) AS approved_order_count,
    COALESCE(SUM(o.total), 0) AS total_spent
FROM users u
LEFT JOIN orders o
    ON o.user_id = u.id
    AND o.status = 'APPROVED'
    AND o.created_at >= CURRENT_TIMESTAMP - INTERVAL '30 days'
GROUP BY u.id, u.name
ORDER BY total_spent DESC;
```

los filtros van en el `ON` y no en el `WHERE`, porque el `WHERE` se ejecuta despues del join y podria quitar las filas donde la compra es NULL, o sea justo los usuarios sin compras, ahi el `LEFT JOIN` termina comportandose como un `INNER JOIN` sin que sea tan obvio

`COALESCE` sirve para reemplazar el NULL por cero, porque `SUM` cuando no hay registros devuelve NULL, en cambio `COUNT(o.id)` ya devuelve 0 porque no cuenta valores NULL

el `GROUP BY` incluye id y name, aunque en PostgreSQL podria bastar con la clave primaria, prefiero dejarlo explicito y no complicarme

PREGUNTA 5 — ÍNDICES Y OPTIMIZACIÓN
===============================================================================

Una tabla orders contiene varios millones de registros y se ejecuta
frecuentemente esta consulta:

SELECT id, user_id, total, created_at
FROM orders
WHERE user_id = :user_id
  AND status = 'APPROVED'
  AND created_at >= :start_date
ORDER BY created_at DESC;

Propón uno o más índices PostgreSQL para mejorarla.

Incluye:

- las sentencias CREATE INDEX;
- el orden de las columnas;
- si utilizarías un índice completo o parcial;
- cómo comprobarías si PostgreSQL utiliza el índice;
- las desventajas de agregar demasiados índices;
- en qué situaciones PostgreSQL podría decidir no utilizar el índice.

RESPUESTA:

primero me fijaria en el orden de las columnas, `user_id` y `status` son filtros de igualdad, mientras que `created_at` es un rango y tambien se usa para ordenar, asi que probaria algo asi

```sql
CREATE INDEX idx_orders_user_status_created
    ON orders (user_id, status, created_at DESC);
```

el `DESC` puede ayudar con el orden de la consulta, aunque PostgreSQL tambien puede recorrer indices en sentido inverso

tambien consideraria un indice parcial, sobre todo si hay muchas ordenes que no estan aprobadas

```sql
CREATE INDEX idx_orders_user_created_approved
    ON orders (user_id, created_at DESC)
    WHERE status = 'APPROVED';
```

este puede ser mas pequeño porque solo guarda las filas aprobadas, pero depende de los datos y de las consultas que se hagan, si necesito traer `total` tambien podria agregar `INCLUDE (total)` para intentar un index-only scan, aunque el indice creceria

para revisar si realmente lo usa probaria `EXPLAIN (ANALYZE, BUFFERS)` y miraria si aparece un Index Scan o Bitmap Index Scan, tambien revisaria las estadisticas, no crearia indices a ciegas

tener demasiados indices tampoco es gratis, ocupan espacio y cada insert, update o delete tiene que mantenerlos, puede aumentar el costo de escritura y el trabajo de mantenimiento

Postgres puede decidir no usarlos si la consulta devuelve muchas filas, la tabla es pequeña, las estadisticas estan desactualizadas o el planner calcula que un Seq Scan sale mas barato, no siempre un indice significa que la consulta va a ser mas rapida

PREGUNTA 7 — APIS HTTP Y CÓDIGOS DE RESPUESTA
===============================================================================

Explica cómo funciona una API HTTP desde que un cliente envía una solicitud
hasta que recibe una respuesta.

Incluye:

- diferencias entre GET, POST, PUT, PATCH y DELETE;
- qué significa que una operación sea idempotente;
- diferencia entre autenticación y autorización;
- diferencia entre los códigos 401 y 403;
- cuándo utilizarías 200, 201, 204, 400, 404, 409, 422 y 500;
- qué información no debería exponerse en una respuesta de error;
- cómo diseñarías una respuesta JSON consistente para errores.

Incluye ejemplos de:

- una solicitud exitosa;
- un error de validación;
- un intento de acceso sin autenticación.

RESPUESTA:

el recorrido seria mas o menos asi, el cliente manda una peticion con metodo, url, headers y body, se resuelve DNS, se establece la conexion y si es HTTPS se negocia TLS, luego el servidor recibe la peticion, pasa por rutas y middleware, llega al controlador, consulta lo que necesita y devuelve una respuesta con status, headers y normalmente un JSON

GET sirve para leer, POST suele crear, PUT reemplaza el recurso completo, PATCH modifica una parte y DELETE elimina, la idempotencia significa que repetir una operacion deja el mismo estado, GET, PUT y DELETE normalmente son idempotentes, POST no necesariamente y PATCH depende de como se haya implementado, esto importa bastante si el cliente reintenta por un fallo de red

autenticacion responde a quien eres, autorizacion a que tienes permiso de hacer, por eso 401 significa que falta o no es valida la autenticacion, y 403 que estas identificado pero no tienes permiso

los codigos que usaria son 200 para una respuesta normal, 201 cuando se crea algo, 204 cuando todo salio bien pero no hay body, 400 para una peticion mal formada, 404 si no existe el recurso, 409 si hay un conflicto, 422 para datos que no pasan validacion y 500 para un error inesperado del servidor, aunque la diferencia entre 400 y 422 depende un poco de las convenciones del equipo

no mostraria stack traces, consultas SQL, rutas internas, tokens, secretos ni detalles que puedan ayudar a atacar el sistema, los errores tendrian un formato estable para que el cliente no tenga que adivinar

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "The given data was invalid.",
    "details": {
      "email": ["The email field is required."]
    }
  }
}
```

un ejemplo exitoso podria devolver 200 con `READER_ACCESS_GRANTED`, una validacion devolveria 422 con ese formato y una peticion sin autenticacion 401 con `SSO_REQUIRED`, lo importante es mantener la misma estructura en toda la API

PREGUNTA 8 — ¿CÓMO APRENDE UNA RED NEURONAL?
===============================================================================

Explica con tus propias palabras qué significa entrenar una red neuronal. Describe 
un ciclo de entrenamiento desde que la red recibe datos hasta que ajusta sus parámetros. 
Incluye qué papel cumplen la predicción, la función de pérdida y la retropropagación.

RESPUESTA:

entrenar una red neuronal es basicamente ajustar sus parametros para que sus respuestas se acerquen a lo esperado, esos parametros son los pesos y sesgos, no es que aprenda reglas como una persona

primero recibe un lote de datos y hace una prediccion, cada neurona combina sus entradas con los pesos, suma el sesgo y aplica una funcion de activacion, al final sale una prediccion, luego la funcion de perdida compara esa salida con la respuesta correcta y calcula que tan lejos estuvo

la retropropagacion calcula como influye cada parametro en ese error usando gradientes y la regla de la cadena, despues el optimizador usa esos gradientes para ajustar los pesos, la tasa de aprendizaje controla cuanto se mueve, si es muy alta puede pasarse y si es muy baja el entrenamiento tarda un monton

esto se repite por lotes y epocas hasta que la perdida mejora, aunque que baje en los datos de entrenamiento no significa que el modelo vaya a funcionar bien con datos nuevos, puede memorizar, por eso tambien se revisa validacion y se vigila el sobreajuste

decir que la red aprende es una forma de hablar, al final esta optimizando una funcion y ajustando numeros, no entiende como lo haria una persona, pero aun asi consigue resultados bastante utiles

¿Qué se entiende por procesamiento del lenguaje natural (PLN) y en qué se diferencia 
una tarea generativa, como redactar un resumen, de una tarea como clasificar el tema de un texto?

Explica qué son los tokens, qué aprende un modelo de lenguaje durante su entrenamiento y 
cómo usa lo aprendido para generar texto. ¿Qué aportan los transformers y el mecanismo de atención?

RESPUESTA:

PLN es el area que busca que las computadoras puedan trabajar con lenguaje humano, por ejemplo traducir, resumir, clasificar o responder preguntas, pero las tareas no son iguales, clasificar un texto es elegir una etiqueta, resumir es generar texto nuevo a partir de lo que le dieron

para generar texto le das un prompt, calcula las probabilidades del siguiente token, selecciona uno y lo agrega, despues vuelve a hacer lo mismo, token por token, por eso puede inventar cosas, genera algo que parece coherente pero no necesariamente es verdad

los transformers usan atencion para que cada token pueda relacionarse con otros tokens del contexto y darle mas importancia a algunos, eso ayuda a captar relaciones que estan lejos dentro del texto y tambien permite procesar partes en paralelo durante el entrenamiento, por ejemplo en "el equipo gano el partido en el ultimo minuto", para interpretar "gano" importan bastante "equipo" y "partido", la atencion ayuda a relacionar esas palabras
